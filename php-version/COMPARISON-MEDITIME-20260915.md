# 출퇴근 기능 비교 — 메디타임과 스몰그룹웨어

기준일: 2026-09-15

## 요약

현재 스몰그룹웨어에는 메디타임과 유사한 **GPS 출퇴근·출장 위치 확인·정정 신청·PC 반영**이 이미 구현되어 있다. 주요 차이는 메디타임의 **설치형 모바일 앱, 야근 계산·결재, 근무자 현황, Notion 연동, 변경 불가 원장과 감사 서명 구조**다.

`meditime-online`과 `meditime-mobile`은 현재 PHP 사이트에 복사해서 자동 연결되는 모듈이 아니다. 둘은 별도의 메디타임 서버와 그 서버 API를 호출하는 앱이다. PHP 서버에 붙이려면 인증·API·직원 식별자·데이터 모델을 연결하는 개발이 필요하다.

## 검토 범위

- 사용자 제공 `C:/Users/user/Downloads/meditime-online.zip` 131개 파일, `meditime-mobile.zip` 32개 파일의 목록 및 주요 소스 확인.
- 비교 대상: 현재 작업 트리의 `php-version/` 근태·인증·화면·DB 코드.
- ZIP은 별도 `.tmp/meditime-comparison-20260915/`에 텍스트 소스만 풀어 검토했다. 앱 설치, 외부 서비스 로그인, ZIP 코드 실행, DB 이전, 기능 변경은 하지 않았다.
- 아래 ‘구현’은 코드에서 확인한 의미다. 첨부 문서의 과거 배포·빌드 성공 주장을 이번에 재검증한 것은 아니다. 실행 속도·실기기 안정성 우열을 평가한 보고서도 아니다.

## 두 ZIP의 관계

| 구성 | 역할 |
| --- | --- |
| meditime-online | 웹 화면 + Google 인증 + JSON API + Cloudflare D1 저장소 + Notion 연동 |
| meditime-mobile | React Native/Expo iOS·Android UI. online의 로그인/조회/저장 API를 호출 |
| 현재 스몰그룹웨어 | PHP 화면·POST 처리 + 기존 직원 계정 + SQLite 로컬 DB / MySQL 운영 대상. 휴대폰도 같은 웹사이트 사용 |

모바일 앱 자체가 PC 사이트에 기록을 복사하는 것이 아니다. 메디타임 웹과 앱이 같은 online 서버를 사용하므로 같은 기록을 본다. 현재 사이트도 PC와 휴대폰이 같은 PHP 서버·DB를 쓰면 같은 기록을 본다.

| 연차·반차 반영 | 승인된 연차 출근 차단, 반차별 근무 기준 반영 | 승인된 종일 휴가 출근 차단, 반차별 근무 기준 표시 |

| 근태 정정 | 정정 요청 + 별도 승인 결정으로 유효 출퇴근을 계산 | 대기 신청 수정·취소, 승인 시 일별 기록 갱신 및 변경 전후 이력 |
| 정정·야근 권한 | 직급에 따른 capability 및 팀/회사/전사 범위, 요청별 canDecide 사용 | 근태 정정은 ADMIN, 자기 신청 처리 금지. 팀장은 휴가 결재 역할 |
| 근무자 확인 | 근무자 현황·조직도·일정·브리핑 UI 및 조회 API | 개인 기록 및 관리자 날짜별/월별 현황 중심 |
| 알림 | 앱/웹 내부 알림 조회·읽음 처리 API | 이번에 비교한 근태 구조에 별도 알림함·읽음 처리 없음 |
| Notion | 근태/결재 등을 D1에서 저장하고 outbox로 Notion 반영·재시도 | Notion 연결 없음 |
| 관리자 출력 | 확인한 근태 UI/API에서는 현재 PHP와 같은 월별 CSV 흐름을 확인하지 못함 | 월·직원·부서·상태 조건을 적용한 근태 CSV |
| 관련 사내 업무 | 캘린더·조직도·체크리스트와 연결 | 직원·연차·법인카드·보고서와 같은 사이트에서 처리 |

메디타임의 야근 계산은 코드상 종료 예정 시각 이후 경과 분을 계산하는 방식이다. 휴게시간·급여 확정까지 처리하는 완성된 급여 엔진으로 해석하면 안 된다. 본 보고서는 근태 기능 비교이며 노동법 적합성을 판단하지 않는다.

## 저장·변경 이력의 차이

### 메디타임

- `attendance_events`는 출근/퇴근 이벤트별 원장이다. D1 초기화 코드에 UPDATE/DELETE를 막는 트리거가 있다.
- 정정 승인 결과를 원래 이벤트 위에 적용해 유효 시각을 계산한다. 원래 GPS 이벤트를 덮어쓰지 않는다.
- 근태 정정·야근 감사 이벤트에 이전 해시, 무결성 해시, HMAC-SHA256 서명 정보를 사용한다. 모든 종류의 DB 변경이 절대 불가능하다는 의미는 아니다.
- 요청 queueId와 변경 시점 검증으로 중복 처리·동시 변경을 방어한다.
- 원좌표는 근태 원장에 두고 일반 응답·Notion outbox에서는 정밀 좌표를 제거하는 코드가 있다.

### 현재 스몰그룹웨어

- `AttendanceDay`가 직원·근무일별 유효 출퇴근을 저장한다. 정정 승인 시 이 행을 갱신한다.
- `AttendanceHistory`는 변경 전후와 처리자·사유·시각을 보관한다. GPS/직접 입력 증거는 별도 테이블에 둔다.
- 원장 UPDATE/DELETE 금지 트리거나 HMAC 감사 체인은 확인되지 않는다. 메디타임과 같은 변경 불가 원장 구조는 아니다.
- 현재도 사용자 잠금, 버전 및 신청 토큰 확인, 중복 출퇴근 차단이 있다. ‘중복 방지가 없다’거나 ‘수정 이력이 없다’는 뜻은 아니다.

## 현재 사이트에 없는 기능 중 도입 후보

1. **미퇴근 복구 동선:** 오래된 출근을 정정 신청만으로 처리할지, 일단 퇴근을 닫고 수정 필요로 분리할지 운영 정책을 정할 수 있다. 단순히 24시간을 20시간으로 바꾸는 작업과는 다르다.
2. **야근 신청·승인:** 실제 업무에 필요하다면 계산 기준, 휴게시간, 승인자, 정정 후 재승인 정책을 먼저 정하고 추가해야 한다. 기존 출퇴근에 숫자만 표시하는 수준보다 범위가 크다.
3. **근무자 현황:** 누가 근무·퇴근·출장 중인지 보여주는 화면을 추가할 수 있다. 직원/팀장/관리자가 각각 볼 범위부터 정해야 한다.
4. **Notion 반영:** 현재 조직에서 Notion에도 근태를 남겨야 할 때만 검토한다. 계정·직원 매핑, 중복 방지, 실패 재시도와 공개 범위가 필요하다.
5. **별도 앱:** 웹 사용과 GPS가 충분하면 필수는 아니다. 앱을 도입하면 API·로그인 호환 개발 외에 Android/iOS 빌드·서명·업데이트 운영이 추가된다.

위 목록은 현재 차이에 따른 도입 후보이며 이번 요청에서 기능 추가를 수행한 것은 아니다.

## 앱을 그대로 붙일 수 없는 구체적인 이유

mobile/src/api.ts는 `/api/auth/mobile/challenge`, `/api/auth/mobile/google`, `/api/auth/session`, `/api/bootstrap`, `/api/sync` 등을 호출하고 JSON 응답을 기대한다. 현재 PHP는 `index.php?page=...` 화면과 폼 POST, 쿠키·CSRF 흐름을 사용한다.

따라서 API 주소만 PHP 주소로 바꾸면 로그인부터 데이터 조회·출퇴근 저장까지 맞지 않는다. 직원 ID와 권한도 서로 다르다. 연결하려면 다음 중 하나를 선택해야 한다.

- 현재 PHP DB·계정을 기준으로 모바일용 인증/API를 만들고 앱의 데이터 계약을 맞춘다.
- 메디타임 서버를 별도로 운영하되 PHP와 데이터·직원 매핑을 연동한다. 양쪽 수정·취소 충돌과 기준 DB를 정해야 하므로 운영 복잡도가 커진다.

두 서버가 각자 출퇴근을 저장하도록만 두는 것은 통합이 아니다. 먼저 어느 DB를 업무 원본으로 사용할지 정해야 한다.

## ZIP에 있는 것과 없는 것

두 ZIP은 소스 묶음이다. 실제 전달 ZIP 목록에는 APK·IPA·iOS 시뮬레이터 앱 압축 파일이 없다. 모바일 README에는 과거 빌드 링크와 배포 이력이 적혀 있지만 그 링크의 현재 유효성이나 실제 앱 설치 가능 여부는 이번에 확인하지 않았다.

Google OAuth, D1, Notion, Expo/Apple 서명 설정은 소스 파일을 복사하는 것만으로 현재 사이트에 적용되지 않는다. 첨부 문서에 계정 연결 완료라고 적혀 있어도 이번 인수 환경에서 별도 확인이 필요하다.
