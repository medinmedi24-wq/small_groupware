# 법인카드 집중 QA — 2026-09-14

기능 코드 변경 없이 독립 SQLite DB와 테스트 계정으로 HTTP 재현 및 Chrome 390px/320px 화면 점검. 실제 직원 데이터와 사용자 휴대폰 테스트 DB는 변경하지 않았다. iPhone 실기기 검증은 이번 점검에 포함하지 않았다.

## 재현 결과

후속 수정: 1·2번 완료. 내역의 금액·내용·증빙·상태를 포함한 검토 토큰을 폼에 넣고, 저장 트랜잭션의 소유자 잠금 후 최신 DB 내용과 비교한다. 승인·반려·수정·취소·증빙 첨부가 모두 동일한 검증을 사용한다. 오래된 수정 폼의 오류 재표시는 기존 토큰을 유지하여 단순 재제출로 충돌을 우회할 수 없도록 했다. 금액 변경 후 오래된 승인/반려, 증빙 변경 후 승인, 오래된 수정 덮어쓰기, CSRF, 최신 내용 재검토 성공을 포함한 HTTP 테스트 357개 통과. 3·4번은 아직 미수정.

1. **[P1] 관리자가 보지 않은 수정 금액을 오래된 승인 폼으로 승인 가능.** 직원 10,000원 등록 → 관리자 승인 폼 보관 → 직원 900,000원 수정 → 기존 폼 제출. HTTP 200, 900,000원이 승인되었다. card_decide는 PENDING 여부만 재검증하며 검토한 내용의 버전을 확인하지 않는다. 금액·사용처·사유·증빙이 바뀌면 기존 승인/반려 요청은 거부하고 재검토해야 한다. app/actions.php card_decide, app/views.php cardTable.

2. **[P2] 오래된 직원 수정 화면이 최신 변경을 덮어쓴다.** 두 직원 세션에서 같은 10,000원 내역을 연 뒤 한쪽에서 20,000원으로 수정하고, 다른 쪽에서 예전 금액을 유지한 채 사유만 수정하면 HTTP 200으로 10,000원에 되돌아간다. card_edit에도 버전 검사나 충돌 안내가 없다. app/actions.php card_edit, app/views.php renderCardForm.

3. **[P3] 영수증 교체 후 이전 파일이 저장소에 누적된다.** 같은 대기 내역에 서로 다른 PDF를 순서대로 첨부하면 DB는 새 파일만 가리키지만 이전 파일도 남는다. 이전 파일을 보는 사용자 이력이나 명시된 보존 정책은 확인되지 않았다. 정상 교체 후 정리하거나 버전 이력으로 관리하는 정책이 필요하다. 실패 시에는 기존 증빙을 보존해야 한다. app/actions.php card_receipt/prepareReceipt.

4. **[P3, 사용성] 좁은 화면의 승인·반려 배치가 불균형하다.** 390px: 승인 56px / 반려 사유 147px / 반려 58px가 한 줄. 320px: 승인만 윗줄, 사유 141px와 반려가 아랫줄. 높이는 모두 44px이고 가로 넘침은 없지만 반려 사유 입력 공간이 좁으며 근태·연차의 사유 전체 폭 + 버튼 두 개 배치와 다르다. app/views.php cardTable, public/assets/php.css approval-controls.

## 통과·범위

후속 수정 2: 3·4번 수정 완료. 모바일에서는 공통 결재 레이아웃을 사용해 사유 전체 폭과 동일 크기 승인·반려 버튼을 배치했다. 320px/390px에서 버튼 높이 44px, 같은 행, 가로 넘침 없음 확인. 영수증 교체는 DB 커밋 후 이전 파일의 참조가 없는지와 저장 디렉터리 안의 실제 파일인지 확인하고 정리한다. 파일 검증 실패 및 강제 DB 롤백 시 기존 증빙을 보존하고 새 업로드를 정리하는 회귀 테스트를 추가했다.
